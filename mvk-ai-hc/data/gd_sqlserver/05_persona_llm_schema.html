Persona/LLM Option Schema

Plain Today, which AI model answers a Doctor or Patient's question is decided by a config file. This schema is the database-backed replacement being built — so that decision can change per user or persona without redeploying the application.
TableRoleWhat it holds
PersonaTypeDimensionThe LLM execution context a request runs under — 1 = Doctor, 2 = Patient. Deliberately separate from Roles (the auth/account concept), not a replacement for it.
LLMOptionDimensionAvailable model/provider/endpoint configurations — mirrors what's currently hardcoded in appsettings.json (HCClassification, HCDocExecutor, HCPatientExecutor).
LLMMapperFactLinks a PersonaType to an LLMOption for a given ModelRole (Classification or Executor), plus generation parameters (MaxTokens, Temperature, TopP, etc.).
PersonaMapperBridgeConnects Roles.RoleId to PersonaType.TypeId, so the two concepts can coexist without merging.

The resolution path already exists as a stored procedure — usp_GetLLMOptionByUserOrPersona — called directly from HC.AI.MAPI.EF.DBContexts.MapiDbContext via a keyless entity:

return LLMOptionResolutions .FromSqlRaw( "EXEC dbo.usp_GetLLMOptionByUserOrPersona @UserId, @PersonaTypeId, @ModelRole", userIdParam, personaTypeIdParam, modelRoleParam) .ToListAsync();

It resolves either by a specific user (walking Users → PersonaMapper → PersonaType) or directly by persona type, optionally filtered to a model role, ordered by IsDefault DESC, Priority ASC.
