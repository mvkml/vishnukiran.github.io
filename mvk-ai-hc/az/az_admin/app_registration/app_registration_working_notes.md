# App Registration Working Notes

These notes capture the current discussion for the future App Registration article.

## Current Focus

We are working on the Azure App Registration article for the employee portal App Service.

The article should move in very small steps and explain the ID chain clearly before entering token/authentication details.

## ID Sequence

### 1. Resource ID

- The employee portal App Service has a resource ID.
- The resource ID is specific to that App Service resource.
- It is a path-like Azure resource identifier.
- This belongs to the Azure resource branch.

### 2. Subscription ID

- The employee portal App Service belongs to one Azure subscription.
- The subscription ID is a GUID.
- It uniquely identifies the Azure subscription.
- The subscription ID is used to identify the subscription that contains the App Service and other Azure resources.

### 3. Tenant ID

- The tenant ID identifies the Microsoft Entra ID tenant.
- A tenant is the identity container for users, groups, and app registrations.
- The App Service is associated with a tenant through the Azure setup/subscription context.
- The tenant ID is not a resource-specific ID like the App Service resource ID.
- It represents the surrounding identity scope.

## App Service vs App Registration

### App Service

The employee portal App Service initially has:

- Resource ID
- Subscription ID
- Tenant context / tenant ID

The App Service does not automatically have a client ID just because it exists.

### App Registration

An app registration lives inside Microsoft Entra ID.

It is part of the identity branch, not the Azure resource branch.

An app registration does not have:

- Azure resource ID
- Subscription ID in the same way an App Service has one

An app registration does have:

- Tenant ID, because it lives inside a tenant
- Application ID / client ID
- Object ID

## Application ID / Client ID

- Application ID and client ID mean the same thing.
- It is a GUID generated by Microsoft Entra ID when an app registration is created.
- We do not manually create the client ID.
- The client ID represents the app registration.
- The App Service itself does not generate this ID.

For the employee portal, when we say "employee portal client ID", we mean the client ID of the app registration created for the employee portal.

## Linking App Service and App Registration

Before app registration:

- Employee portal App Service has no client ID for authentication use.

After app registration:

- Microsoft Entra ID generates a client ID for the employee portal app registration.
- The App Service can be configured to use that app registration for authentication.
- After configuration, the App Service authentication settings can show/reference the client ID.
- The client ID still belongs to the app registration.
- The App Service only points to or uses that client ID.

## Analogy

Use this analogy carefully:

- Microsoft Entra ID tenant = security department / identity authority
- App registration = the application's identity profile or ID-card record
- Client ID = the ID number on that application identity profile
- Employee portal App Service = the hosted application/service

Important correction:

- One app registration represents one application.
- It is not a grouping of applications.
- "Profile" means one identity record for one registered app.

The user does not need to carry the client ID manually.

## Level Zero Browser Flow Before Authentication

Current frozen point:

- User has not entered username or password yet.
- Browser does not already have the client ID sitting inside it.
- User only types the employee portal URL and presses Enter.
- The browser first asks for the employee portal page.
- The App Service later responds with authentication redirect information if authentication is required.
- That redirect can include the client ID and other Entra sign-in details.

## Important Correction: Azure Portal vs App Service

Azure Portal is only the management UI.

The runtime user flow is not:

```text
User -> Azure Portal -> App Service
```

The runtime user flow is closer to:

```text
User browser -> DNS/network path -> Azure infrastructure -> Employee Portal App Service
```

For the authentication article, we can treat the employee portal App Service as the first application-level gate.

Before the request reaches the App Service, there are lower-level network steps such as:

- Browser
- Wi-Fi / local router
- DNS resolver
- Internet routing
- Azure front-end infrastructure

## DNS Learning Notes

DNS stands for Domain Name System.

Analogy:

- Website name / domain name = person's name
- IP address = phone number
- DNS = phone book system that finds the phone number for the name

Important corrections:

- DNS is not a single server.
- DNS is not one government-style central organization that owns all mappings.
- DNS is a distributed system made up of many servers run by many organizations.
- The Wi-Fi router may have DNS settings and may forward DNS queries.
- The Wi-Fi router may have a temporary cached DNS answer, but we should not assume it always has the IP address.
- DNS does not exactly redirect the browser.
- DNS resolves a hostname into address information.
- After DNS returns the address, the browser uses that address to connect toward the Azure infrastructure hosting the App Service.

Simplified frozen flow:

```text
User types URL
Browser sends request through Wi-Fi/local router
DNS system is used to find the address for the hostname
DNS returns address information
Browser can then connect toward Azure infrastructure
```

Do not go deeper into authoritative DNS, recursive resolvers, root servers, or CNAME records yet unless needed later.
