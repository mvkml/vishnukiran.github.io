Local-First Workflow

Plain New work is planned as a plain markdown file first — an Epic, a User Story, a Task — and only pushed into Azure DevOps once that plan is settled and someone explicitly asks for it to be synced. Azure DevOps is the record of what's confirmed, not the scratchpad for what's still being figured out.
hc_agile/ ├── product_owner/ │ ├── epics/EPIC00N_*.md │ ├── user_stories/US0NN_*.md │ └── backlog/BACKLOG.md ← running list, PB0NN entries └── scrum/tasks/TASK0NN_*.md ← execution-level breakdown

Only once a plan here is settled does it get mirrored into Azure DevOps as an Epic/Issue, with the local file updated to link back to the live work-item URL.

Why this order, not the reverse

  • Drafting is cheap and reversible in markdown — renaming, restructuring, or discarding an idea costs nothing. Doing the same in Azure DevOps means editing or deleting a work item with a permanent ID and audit history.
  • With several contributors (including concurrent AI-assisted sessions) editing this repository at once, ID collisions on US0NN/TASK0NN/PB0NN happen in practice — caught by re-checking the live folder listing immediately before assigning a new ID, not by any tooling. Reconciling a naming collision in local files is far cheaper than reconciling two different Azure DevOps work items that both claim the same intent.
  • It keeps Azure DevOps signal-to-noise high — every Epic/Issue that exists there represents work someone has actually decided to track externally, not every idea that was ever typed out.
