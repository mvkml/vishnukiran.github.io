1. What is an ORM, and what is Entity Framework Core

Plain An application needs to read and write data in a database. Without help, a developer writes raw SQL for every operation and manually converts each database row into a C# object, and back again. An ORM (Object-Relational Mapper) automates that translation — the developer works with plain C# classes, and the ORM generates the SQL underneath.
Technical Entity Framework Core (EF Core) is Microsoft's ORM for .NET. It maps C# classes ("entities") to database tables, tracks changes made to those objects in memory, and generates the corresponding SQL (INSERT/UPDATE/DELETE/ parameterized SELECT) when changes are saved. It supports multiple database providers (SQL Server, PostgreSQL, SQLite, etc.) through a common API, and includes a migrations system for evolving the database schema alongside the codebase.

2. Why this project uses it

Plain Every backend API in this project that talks to a database (HC.AI.Identity.Api today, HC.AI.MAPI and AI.HealthCare.Patient.API following the same pattern) needs a consistent, reliable way to read/write records — users, roles, documents, and (in HC.AI.MAPI's case) the persona/LLM-configuration tables discussed elsewhere in this project. EF Core gives every API the same approach instead of each one inventing its own data-access code.
Technical This project standardizes on EF Core 8 with the SQL Server provider across its .NET APIs, using a code-first, migration-driven workflow — the C# entity classes are the source of truth, and schema changes are captured as versioned migration files (not hand-written ALTER TABLE scripts run ad hoc). This keeps schema history in source control alongside the code that depends on it.

3. The three building blocks

Plain Setting up EF Core for a new area of the database comes down to three things: (1) plain C# classes describing what a record looks like, (2) one class that represents "the database connection plus what tables exist," and (3) a way to tell the app how to actually connect (which server, which database).

3a. Entity classes

Plain C# classes, one per table, living under Entities/:

// HC.AI.Identity.EF/Entities/Role.cs (simplified)
public class Role
{
    public int RoleId { get; set; }
    public string RoleName { get; set; }
    public int OrderId { get; set; }
    public ICollection<User> Users { get; set; }
}

3b. The DbContext

One class per logical database, exposing a DbSet<T> per entity, plus Fluent API configuration (keys, required fields, max lengths, indexes, relationships, seed data) in OnModelCreating:

// HC.AI.Identity.EF/DBContexts/AiHrDbContext.cs (excerpt)
public class AiHrDbContext : DbContext
{
    public AiHrDbContext(DbContextOptions<AiHrDbContext> options) : base(options) { }

    public DbSet<User> Users => Set<User>();
    public DbSet<Role> Roles => Set<Role>();
    public DbSet<OcrDocument> OcrDocuments => Set<OcrDocument>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Role>(e =>
        {
            e.HasKey(r => r.RoleId);
            e.Property(r => r.RoleName).IsRequired().HasMaxLength(100);
            e.HasIndex(r => r.RoleName).IsUnique();
        });

        modelBuilder.Entity<User>(e =>
        {
            e.HasKey(u => u.UserId);
            e.HasOne(u => u.Role).WithMany(r => r.Users).HasForeignKey(u => u.RoleId);
        });

        // Seed data — rows created automatically by the next migration
        modelBuilder.Entity<Role>().HasData(
            new Role { RoleId = 1, RoleName = "Doctor", OrderId = 1 },
            new Role { RoleId = 2, RoleName = "Patient", OrderId = 2 }
        );
    }
}

3c. Registering it in the API

One line in Program.cs wires the DbContext into dependency injection, pointing at a named connection string:

builder.Services.AddDbContext<AiHrDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("AiHrDb")));

4. Step-by-step: setting up EF Core for a new API area

Plain Once the three building blocks above exist, there's a repeatable set of commands to get a real database table out of them, and to change that table later without losing data.
  1. Add the NuGet packages (as done in HC.AI.Identity.EF.csproj): Microsoft.EntityFrameworkCore.SqlServer, Microsoft.EntityFrameworkCore.Design, Microsoft.EntityFrameworkCore.Tools — all pinned to 8.0.28 in this project.
  2. Write the entity class(es) under Entities/.
  3. Write (or extend) the DbContext, registering each entity as a DbSet<T> and configuring it in OnModelCreating.
  4. Add a connection string to appsettings.json under a named key (e.g. AiHrDb), and register the DbContext in Program.cs as shown in 3c.
  5. Generate a migration: 
    dotnet ef migrations add <DescriptiveName> --project <EFProjectFolder> --startup-project <ApiProjectFolder>
    This project's real migration history for AiHrDbContext (in order): InitialCreate → AddRoleOrderId → AddOcrDocumentsTable → AddUserUpdatedAt → SimplifyRolesToDoctorPatient — each one a small, named, incremental change, not one giant schema dump.
  6. Apply the migration to the actual database: 
    dotnet ef database update --project <EFProjectFolder> --startup-project <ApiProjectFolder>
  7. From then on, any further schema change is: change the entity/DbContext → generate a new migration → apply it. The migration files are checked into source control, so the schema's full history travels with the code.

5. Why this approach matters

Plain Because the schema lives in code and every change is a tracked, named migration, it's possible to show exactly when and why any table changed, not just what it looks like today.
Technical The SimplifyRolesToDoctorPatient migration is a real, traceable example of a deliberate business decision (narrowing roles from a generic 7-role HR set down to just Doctor/Patient) captured as a schema change with a self-documenting name, sitting alongside the reasoning for it in hc_agile/product_owner/backlog/BACKLOG.md (PB023 notes). That pairing — code-first schema plus the documented business reasoning — means the schema's technical history and its business rationale stay in sync, from the same source of truth.
