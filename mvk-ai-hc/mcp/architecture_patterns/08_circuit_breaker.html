Circuit Breaker

Resilience Pattern Planned Implementation Relevant Risk Observed
Plain: A Circuit Breaker protects the application from repeatedly calling something that is already failing. After enough failures, the circuit opens for a short time, stops new calls, and lets the system recover instead of making every request wait and fail again.

What It Is

Circuit Breaker is a resilience pattern used around remote calls: APIs, databases, model runtimes, queues, or any service that can be slow, unavailable, or overloaded. It behaves like an electrical breaker. When failures cross a threshold, the circuit opens and blocks more calls for a cooling period.

After the cooling period, the breaker allows a small test call. If that succeeds, the circuit closes and normal traffic resumes. If it still fails, the circuit opens again.

Why We Use It

Without a Circuit Breaker, every user request may repeat the same doomed call and wait for a timeout. That wastes threads, keeps the UI waiting, increases load on the failing service, and turns one dependency problem into a wider application problem.

With a Circuit Breaker, the system can fail fast with a clear scoped message, use a fallback, or route the request differently while the failing dependency recovers.

When To Use It

Use it when the application calls something outside its own process and that dependency can fail repeatedly: an MCP host, an LLM runtime like Ollama, an external EHR API, a payment or insurance service, or a database path with known transient failures.

How It Works

1. Closed
Normal operating state

The application calls the dependency normally.

Successes and failures are counted in the background.

If failures stay below the threshold, the circuit remains closed.

2. Open
Protection state

Too many failures or timeouts have happened within the configured window.

The breaker stops sending new calls to the failing dependency.

The application fails fast with a controlled fallback or scoped message.

3. Half-Open
Recovery test state

After the cool-down period, the breaker allows a small test call.

If the test succeeds, the circuit closes and normal traffic resumes.

If the test fails, the circuit opens again and waits before trying later.

Relevant Project Context

The project has already observed a real resilience risk around local Ollama generation. BUG-001 records cold-start or slow-generation requests taking around 90-110 seconds and sometimes exceeding the default HttpClient timeout. BUG-005 also records model switching/residency uncertainty when moving between Doctor and Patient persona models.

This is exactly the kind of dependency behavior where Circuit Breaker and Retry policies become useful: the model runtime may be temporarily unavailable, too slow, or not ready for the next request. The current project has mitigations, but not a full breaker yet.

What We Have Achieved

The project has not yet implemented a formal Circuit Breaker in code. There is no completed Polly-based breaker around Ollama or MCP calls today.

What has been achieved is the groundwork and practical mitigation around the same failure area: the timeout issue is logged as BUG-001, Doctor and Patient pre-warm endpoints were added to reduce first-message cold-start pain, the demo pre-warm script was created, and QA documented that pre-warming helps but does not fully solve CPU-only slow generation.

Planned MCP Host Use

ADR004 applies Circuit Breaker to future separated MCP hosts. If the ICU MCP host is down, the Doctor agent should not keep waiting on repeated failed ICU calls, and unrelated OP queries should still work. A gateway or BFF can put a breaker around each host and return a clear scoped failure only for the unavailable domain.

Related Patterns

  • Retry Pattern

    What it means: retry the same operation when the failure may be temporary.

    How it relates: Retry can handle a short Ollama/MCP hiccup, but Circuit Breaker stops retries when the dependency is clearly unhealthy.

  • Timeout Pattern

    What it means: set a maximum wait time for a dependency call.

    How it relates: BUG-001 is a timeout problem. Circuit Breaker uses timeout failures as signals to open the circuit after repeated trouble.

  • Fallback Pattern

    What it means: return a safe alternate response when the primary path is unavailable.

    How it relates: If an ICU MCP host is down, the agent can return a scoped message such as "ICU tools are temporarily unavailable" instead of failing the whole chat.

  • Bulkhead Pattern

    What it means: isolate resources or failure domains so one area does not sink another.

    How it relates: Bulkhead separates OP/ICU/Emergency capacity; Circuit Breaker decides when one failing domain should stop receiving calls for a while.

  • API Gateway / BFF Pattern

    What it means: provide one controlled entry point for a client or agent.

    How it relates: A Gateway or BFF is a natural place to apply Circuit Breaker policy for each downstream MCP host.

  • Health Check Pattern

    What it means: actively check whether a service is alive, ready, and able to handle traffic.

    How it relates: Health checks can inform whether an MCP host or Ollama path is ready before the breaker allows traffic again.

  • Rate Limiting Pattern

    What it means: restrict how many calls a client or workflow can make in a period of time.

    How it relates: Rate limiting reduces overload; Circuit Breaker reacts when overload or failure has already started to damage dependency calls.

Terminology

Closed Circuit
Normal state. Calls are allowed and success/failure is tracked.
Open Circuit
Protected state. Calls are blocked temporarily because failures crossed the threshold.
Half-Open Circuit
Recovery test state. A small number of calls are allowed to check if the dependency is healthy again.
Failure Threshold
The number or percentage of failures required before the circuit opens.
Cool-Down Period
The waiting time before the breaker tests the dependency again.
Fail Fast
Return quickly with a controlled response instead of waiting for another likely timeout.
Scoped Failure
A failure limited to one dependency or domain, such as ICU tools only, while other domains continue.
Transient Failure
A short-lived failure that may succeed on retry, such as a brief network or service hiccup.
