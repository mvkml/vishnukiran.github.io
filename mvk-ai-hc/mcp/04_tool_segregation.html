MCP Tool Segregation By Host Boundary

ADR004 Future Decision Not Built Yet
Plain As Healthcare Co-Pilot Studio grows, not every agent should see every healthcare tool. A Doctor agent working with outpatient data should not be overloaded with ICU or Emergency tools unless that scope is intentionally allowed. The architecture decision is to isolate future tool groups by separate MCP host projects, not by naming convention or URL structure.
Current status: this is a decision for future work. Today's HC.AI.MCP host still has one tool/domain path. Nothing is currently segregated; this page documents the approved approach for when a second patient tool category is added.

Why Changing The URL Is Not Enough

Technical In the current MCP ASP.NET Core SDK shape, REST routing and MCP tool visibility are separate concerns. Changing a controller route or mapping MCP at a different URL does not create a different tool list. Tool exposure comes from the MCP server registration and the assembly scanned by WithToolsFromAssembly(). Multiple routes can still point to the same global MCP tool registry.

Why Client-Side Filtering Is Not Enough

Enterprise Concern Client-side filtering means the agent chooses to ignore tools it should not use. That can work in a small prototype, but it is not a strong enterprise trust boundary. A different client, a later code change, or another team can accidentally expose or call a tool that the server still makes available.

Chosen Approach

HC.AI.MCP.Patient.OP -> OP patient tools only HC.AI.MCP.Patient.ICU -> ICU patient tools only HC.AI.MCP.Patient.Emergency -> Emergency patient tools only
DecisionValue
Separate MCP host per bounded contextEach agent connects only to the host relevant to its domain.
Shared class libraries for common logicRepository, EF, BL, and model conventions can still be reused.
Separate deployable processes/portsAuth, scaling, ownership, and release cadence can differ per domain.
Structural isolationAn agent cannot see tools from a host it was never connected to.
Client-facing takeaway: this maps MCP tool design to standard microservice and bounded-context architecture. Tool segregation becomes a deployment and ownership boundary, not an instruction that every client must remember to follow. The detailed technical architecture patterns are expanded in MCP Architecture Patterns.
