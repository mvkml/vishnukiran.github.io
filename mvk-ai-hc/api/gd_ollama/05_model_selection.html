Model Selection: Config vs. Database

Plain Which Ollama model actually answers a given request is never a hardcoded name in the business logic. Today that decision is made from a config file; a database-backed replacement is built and callable, but not yet the default.

Path A — config-section lookup (live today)

Each endpoint is mapped to a named appsettings.json section (HCDocExecutor, HCPatientExecutor, …) via a PersonaKey string set in the request mapper, then bound directly:

public LLMOptionItem GetLLMOptions(string persona) { var options = new LLMOptionItem(); _configuration.GetSection(persona).Bind(options); return options; }

Path B — database-backed (built, not yet default)

The same lookup can instead resolve from SQL Server — dbo.LLMOption joined through dbo.LLMMapper, scoped to the authenticated user's persona and the requested model role (Classification/Executor), via the stored procedure usp_GetLLMOptionByUserOrPersona. See the SQL Server section for the schema. This path is genuinely dynamic — the model name becomes a database value resolved per request, not a compiled constant — but has no seed data checked into source control yet.

When a request has no authenticated user (no UserId — an edge case, not the expected path), it falls back to a third pair of config sections, FBDoctorExecutor/FBPatientExecutor — see Current Status for a real bug found in that fallback configuration.
