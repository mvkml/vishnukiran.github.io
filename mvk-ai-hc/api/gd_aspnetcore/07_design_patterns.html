Design Patterns

Plain Every backend API in this platform is built from the same small set of layers — Controller, Service, Business Logic, Agent, and Entity Framework — and each layer boundary uses a well-established design pattern to keep concerns separated and pieces replaceable.
Controller ← top / highest layer (faces the outside world — HTTP, the caller) Service Business Logic Agent Entity Framework ← bottom / lowest layer (faces the database — nothing below it)
Design PatternWhat it solvesWhere it shows up
Layered / N-Tier ArchitectureKeeps each concern isolated — a change in one layer shouldn't ripple through the othersThe chain itself: Controller → Service → Business Logic → Agent → Entity Framework
Dependency InjectionEvery layer depends on an interface, not a concrete implementation, so pieces can be swapped or tested in isolationWired at startup, used throughout every layer
Repository PatternIsolates "how we talk to the database" from "what the business logic needs"Sits directly above Entity Framework
Factory PatternBuilds the right object at runtime based on configuration, instead of hardcoding one fixed choiceBuilds the language-model client based on which provider/model is configured
Mapper / Data Mapper PatternTranslates a request or database result from one layer's shape into the next layer's shape, so the two can evolve independentlyBetween almost every layer boundary
DTO (Data Transfer Object) PatternSeparate objects for "what came in over the wire," "what a layer works with internally," and "what goes back out" — instead of one object doing all three jobsRequest / internal item / response, at each layer
Allow-List (Whitelist) PatternA security pattern — instead of trying to block bad input, only pre-approved input is allowed through at allThe query-safety design in the data layer (approved tables, columns, and joins only)
Fallback / Default PatternA safe secondary path when the expected context is missing, instead of failing outrightUsed when a request arrives without full identity context
Adapter PatternLets the system talk to different underlying providers through one consistent interfaceThe layer that talks to the language-model runtime is written against a provider-agnostic interface

Most of these are structural/architectural patterns — how layers relate to each other — rather than classic behavioral "Gang of Four" patterns. That matches this codebase's overall style: pragmatic layering, not pattern-naming for its own sake.

Not yet present, honestly: even though the design docs describe it, there is no Strategy pattern for model routing yet — a step that would pick between a "classification" model and an "executor" model at runtime. That routing decision is planned, not built.
