NuGet Packages — What Each One Is Responsible For

Plain Entity Framework Core itself is split across a few separate installable packages rather than one giant package — one does the actual work of talking to SQL Server at runtime, and two others exist purely to power the command-line tools used while developing (generating and applying migrations). Only one of the three needs to ship with the running application.
Technical This project references three EF Core packages (all pinned to 8.0.28 in HC.AI.Identity.EF.csproj) — each with a distinct, non-overlapping responsibility:
PackageResponsibilityWhen it's needed
Microsoft.EntityFrameworkCore.SqlServer The SQL Server database provider for EF Core. Translates EF Core's LINQ queries into actual SQL Server T-SQL, provides the UseSqlServer(...) extension method used when registering the DbContext, and handles SQL-Server-specific type mapping (e.g. NVARCHAR, DATETIME2). Runtime — the app cannot connect to or query SQL Server without it.
Microsoft.EntityFrameworkCore.Design Shared design-time infrastructure that the EF Core CLI tooling depends on to inspect the model, build migrations, and scaffold code. Design-time only — marked PrivateAssets="all" in the csproj, so it doesn't ship inside the published application.
Microsoft.EntityFrameworkCore.Tools Provides the actual dotnet ef command-line commands (migrations add, database update, etc.) used throughout the Setup Steps workflow. Design-time only — same PrivateAssets="all" treatment; a developer's machine needs it, the deployed application doesn't.
Plain In short: one package is the "driver" that lets the running application actually talk to the database; the other two are developer-only tools that never leave the build machine.

1. Microsoft.EntityFrameworkCore.SqlServer

What it is: the SQL Server "database provider" — the plug-in that teaches generic EF Core how to speak SQL Server specifically (as opposed to PostgreSQL, SQLite, etc., which would each need their own provider package instead).

Responsibility: turns the LINQ queries written against a DbSet<T> into real, parameterized SQL Server T-SQL, and maps C# types to SQL Server column types (e.g. C# string → NVARCHAR, C# DateTime → DATETIME2).

Example — this project's actual registration in Program.cs, where UseSqlServer comes directly from this package:

builder.Services.AddDbContext<AiHrDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("AiHrDb")));

And the query this provider makes possible — plain C# on the left, what it becomes on SQL Server on the right:

// C# (LINQ) — no SQL written by hand
var user = await context.Users
    .FirstOrDefaultAsync(u => u.Email == email);

// Translated to (conceptually):
// SELECT TOP(1) * FROM Users WHERE Email = @email

2. Microsoft.EntityFrameworkCore.Design

What it is: the shared design-time engine that EF Core's developer tooling is built on top of — it does the actual work of inspecting the model and building a migration; it is not something application code calls directly.

Responsibility: at design time (i.e. while a developer is running a command, not while the app is serving requests), it loads the DbContext, compares the current model against the last migration snapshot, and produces the C# migration file describing the difference.

Example: this package is what makes the next command (migrations add) able to see the model at all — without it installed, running the command from Setup Steps fails immediately with a missing design-time-services error, before it even gets to generating anything:

dotnet ef migrations add AddUserUpdatedAt --project HC.AI.Identity.EF --startup-project HC.AI.Identity.Api
# ^ Microsoft.EntityFrameworkCore.Design is what allows this command to load
#   AiHrDbContext's model and compute what changed, producing:
#   Migrations/20260704033222_AddUserUpdatedAt.cs

3. Microsoft.EntityFrameworkCore.Tools

What it is: the command-line front-end — literally what makes the dotnet ef command exist and recognize its sub-commands.

Responsibility: parses the command line (migrations add, database update, migrations remove, etc.) and hands the request off to Microsoft.EntityFrameworkCore.Design to do the actual work.

Example — the second half of the real workflow from Setup Steps, applying a generated migration to the actual database:

dotnet ef database update --project HC.AI.Identity.EF --startup-project HC.AI.Identity.Api
# ^ Microsoft.EntityFrameworkCore.Tools provides the "dotnet ef" command itself;
#   without this package, "dotnet ef" is not a recognized command at all.
