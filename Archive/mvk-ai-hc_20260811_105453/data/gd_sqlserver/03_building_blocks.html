Building Blocks

Plain Four APIs, one database, two ways the schema gets built — Entity Framework migrations own most of it, and a small, deliberate set of hand-written SQL scripts own the rest.

Connection strings (one LocalDB instance, shared)

APIConnection keyValue
HC.AI.Identity.ApiAiHrDbServer=(localdb)\MSSQLLocalDB;Database=AI_HealthCarePatient;...
HC.AI.Admin.APIAdminDbsame server/database
AI.HealthCare.Patient.APIPatientDbsame server/database
HC.AI.MAPIMapiDbsame server/database

Each API registers its own DbContext against its own connection-string key — e.g. HC.AI.MAPI/Program.cs:

builder.Services.AddDbContext<MapiDbContext>(options => options.UseSqlServer(builder.Configuration.GetConnectionString("MapiDb")));

EF Core-managed tables (schema owned by migrations)

  • Auth — Users, Roles, OcrDocuments (HC.AI.Identity.EF, 5 migrations)
  • Admin — Admins (HC.AI.Admin.EF)
  • Clinical/patient data — 18 tables including Patients, Encounters, Conditions, Claims, Providers, Observations (AI.HealthCare.Patient.EF, 18 migrations, sourced from the Synthea synthetic dataset)

These are created and updated with dotnet ef database update — the matching .sql files under hc_data_source/hc_sql/tables/ for this group exist only as human-readable reference copies, not the DDL actually run.

Hand-written DDL tables (no EF entity at all)

TablePurpose
TableWhitelist, ColumnWhitelist, JoinWhitelistServer-side allow-list of what the AI assistant may query — see next topic
QueryAuditLogOne row per AI-driven query execution, for compliance traceability
PersonaType, LLMOption, LLMMapper, PersonaMapperConfiguration schema for dynamic model selection — see Persona/LLM Option Schema

Run order for these scripts, per hc_data_source/hc_sql/README.md: tables/ → seed/ → procedures/.
