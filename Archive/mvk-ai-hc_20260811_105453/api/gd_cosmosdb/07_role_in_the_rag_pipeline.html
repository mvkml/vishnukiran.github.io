Role in the RAG Pipeline

Plain Retrieval-Augmented Generation means the assistant looks something up before answering, instead of answering from the model's training alone. Cosmos DB is where the "something to look up" would live — but the lookup step itself doesn't exist in the code yet either.

The analysis behind this (US033) breaks the missing pipeline into layers, mapped against what already exists in HC.AI.MAPI today:

LayerWhat it needsStatus
Embedding generationAn embedding model + Semantic Kernel connector to turn text into vectorsNot started — likely a local Ollama embedding model (e.g. nomic-embed-text), version compatibility with the current SK package not yet checked
Vector storeSomewhere to persist embeddings + source-chunk metadataDecided: Cosmos DB, on-premise emulator
Document storageSomewhere to hold raw source documents before chunkingDecided: Storage Account emulator (Azurite)
Ingestion pipelineA process to chunk documents and write embeddings + metadata into Cosmos DBNot designed — corpus (what documents, exactly) not yet chosen
Retrieval stepEmbed the incoming query, similarity-search Cosmos DB, inject top matches into the promptNot built — natural insertion point identified as SemanticProcessService, the layer that currently builds the prompt just before calling the Kernel
Persona scopingDoctor and Patient likely need different, permission-scoped retrieval resultsNot designed — existing PromptItem.UserId/PersonaKey identity plumbing (already built for LLM-option resolution) is the likely template to extend

Where this sits relative to the two pieces already documented elsewhere: Cosmos DB would become a new data source that Semantic Kernel's orchestration reads from before calling Ollama — a genuine new stage in that chain, not a replacement for either.
