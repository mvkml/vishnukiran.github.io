Vector Database Capabilities

Plain A "vector database" is a store that can find records by meaning, not just by exact match — the same technology that lets an AI assistant find the right paragraph in a document even when the question doesn't share a single word with it.

What a vector/embedding actually is

An embedding model turns a piece of text into a list of numbers (a vector) that captures its meaning — texts with similar meaning end up with vectors that are numerically close together, even if the wording is completely different. "Post-surgery allergic reaction" and "adverse response following an operation" would land near each other in that number space, despite sharing almost no words.

How Cosmos DB supports this

CapabilityWhat it does
Vector field on a documentAn embedding (the list of numbers) is stored as a regular field on the same JSON document as its source text and metadata — no separate system to keep in sync
Vector indexA specialized index built over that field, so a similarity search doesn't have to scan every document
Similarity searchA query asks for the N documents whose vectors are numerically closest to a given query vector — "find what's semantically closest to this question," not "find an exact text match"

Conceptually, a retrieval query looks like: embed the incoming question into a vector, then ask Cosmos DB for the top handful of stored chunks whose vectors are closest to it — those chunks are what get handed to the language model as grounding context before it answers.

Why this matters for RAG specifically

Because the vector index and the source text/metadata live in the same document in the same database, there's no separate vector-database product to stand up and keep synchronized with a separate metadata store — one query returns both "how relevant is this" and "here's the actual content," together.
