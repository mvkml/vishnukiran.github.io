Semi-Structured Data & the NoSQL Model

Plain A SQL Server table wants every row to have the same fixed columns. Cosmos DB doesn't ask for that — it stores JSON documents, and different documents in the same container are allowed to have completely different fields. That flexibility is the whole point of "semi-structured" data.

What "semi-structured" means here

Data has some organization (it's not just raw text) but doesn't fit a single rigid schema — fields can be nested, optional, or vary between records. A JSON document is the classic example:

{ "id": "chunk-00147", "sourceType": "clinical-guideline", "title": "Post-operative allergy monitoring", "content": "…the chunk of source text…", "tags": ["allergy", "post-op"], "embedding": [0.0142, -0.0873, 0.0561, "… 1536 numbers total"] }

A different record in the same container — say, one sourced from a different kind of document — might have entirely different fields alongside id and embedding. A relational table can't easily hold both shapes side by side without either a wide table full of unused nullable columns, or a schema migration every time a new document type shows up. A JSON-document container just holds both, as-is.

ConceptWhat it is
ContainerRoughly the NoSQL equivalent of a table — a set of JSON items, but without a fixed column schema
ItemA single JSON document — the equivalent of a row, but self-describing rather than schema-bound
Partition keyA field chosen per container that Cosmos DB uses to spread data (and throughput) across physical partitions — critical for both performance and cost at scale
Schema-on-readThe application, not the database engine, decides how to interpret a document's fields — the database doesn't enforce a schema up front

This is exactly the shape RAG source data naturally takes: chunks pulled from different kinds of documents, each with its own metadata fields, all needing to sit next to a vector embedding — see Vector Database Capabilities.
