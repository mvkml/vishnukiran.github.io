Orchestration Flow

Plain When a Doctor sends a message through the current, locked chat endpoint, it passes through several small, single-purpose layers — each one only responsible for one step — before it ever reaches the language model.
DoctorController.ProvidePrompt → IDoctorService.ProvidePromptAsync (DoctorService.cs) → IDoctorPromptMapper.ToPromptItem (builds PromptItem, ModelRole = "Executor") → ILLMModelBL.GetModelDetailsAsync (resolves LLMOptionItem — DB, falling back to config if no UserId) → IDoctorSemanticProcess.ProcessAsync (DoctorSemanticProcess.cs — builds the system-prompt + user-message template) → ISemanticProcessService.ExecutePromptAsync (SemanticProcessService.cs) → IKernalFactory.CreateKernel (KernalFactory.cs — builds the Kernel) → kernel.InvokeAsync(...) (Semantic Kernel → Ollama) → PromptResponse (bubbles back up through every layer)

Two things worth calling out about this chain:

  • Persona symmetry: PatientSemanticProcess mirrors DoctorSemanticProcess exactly — same shape, own persona-specific prompt provider injected in. It's a fully implemented sibling, not a stub waiting to be built.
  • No tool-calling in this chain: the Prompt Layer contributes only a static system-prompt string, concatenated into one flat template before the Kernel call — there's no ChatHistory role separation and no plugin/function-calling step here. What that means in more detail is covered next in Design vs. Reality.
