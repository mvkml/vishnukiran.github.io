Design vs. Reality

Plain The original technical design for this system described a more ambitious capability than what's running today — that's normal for a project built incrementally, but it's worth stating plainly which parts are still just the plan, not the product.

The design document (hc_agile/architecture/design_patterns/healthcare_ai_assistant_semantic_kernel_design.md) describes the model actively calling registered tools/plugins to look up real patient data before answering. That mechanism does not exist in the running code today:

DesignedActually built
kernel.Plugins.AddFromObject(...) registering a HealthcareQueryPlugin No plugins are registered on any Kernel anywhere in the codebase
[KernelFunction]-attributed tool methods the model can call None exist
FunctionChoiceBehavior.Auto() driving automatic tool-calling Not used — every Kernel call is a single plain-text prompt-in, text-out completion
Model grounds its answer in real database query results Model answers from the prompt text alone — no query executes as part of this flow

This connects to two other pieces of the system that are present in the codebase but not yet wired into the Semantic Kernel flow:

  • HC.AI.MAPI.Guardrail — referenced by the project, but currently an empty stub with zero implementation files.
  • HC.AI.MAPI.Tool — exists and is used, but only for request-shape validation before the Kernel call, not as a Kernel plugin the model can invoke.

The Classification → Executor multi-agent routing described elsewhere in this project's planning (see the persona/LLM configuration work) is similarly not part of this live flow — every request today is hardcoded to the Executor role. A separate mechanism proves the resolution logic works, but its own code comments describe it as not part of any locked or live feature.
