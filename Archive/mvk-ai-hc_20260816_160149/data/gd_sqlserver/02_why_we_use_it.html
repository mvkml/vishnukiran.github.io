Why We Use It

Plain Healthcare data is deeply relational — a patient has encounters, an encounter has conditions and procedures, a claim references both a patient and a provider. A relational database is a natural fit for keeping those connections consistent and enforceable.
  • Strong relationships, enforced by the database itself. Foreign keys between Patients, Encounters, Conditions, Claims, and the rest of the clinical schema mean an orphaned record (a claim pointing at a patient that doesn't exist) simply can't happen.
  • First-class EF Core support. Every .NET API in this platform already uses Entity Framework Core; SQL Server is EF's most mature, best-supported provider.
  • A safe place to enforce access rules server-side. The AI assistant's query engine (see The Query-Guardrail Procedure) depends on being able to define, in the database itself, exactly which tables, columns, and joins a request is allowed to touch — independent of whatever the calling code does.
  • One local instance, zero extra infrastructure. LocalDB runs alongside the APIs during development with no separate server to stand up, while still being the same SQL Server engine used in production deployments.
