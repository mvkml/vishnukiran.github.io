Frontend Token Handling

Plain Once the browser has the token, two things need to happen automatically: it needs to be remembered across the session, and it needs to be attached to every API call the app makes — without every single feature having to remember to do that itself.

Storing the session

Technical hc_ui/aihcweb/src/app/features/auth/data/auth.service.ts stores { user, token } as JSON in localStorage under the key hc_auth_session. The code's own comments flag this as a pragmatic choice made to unblock development, not a signed-off security decision — an httpOnly cookie was considered as the more secure alternative but needs explicit Architect/Product Owner sign-off before switching.

Attaching it to every request

A functional HTTP interceptor does this automatically, so individual feature code never manually adds the header:

// auth.interceptor.ts (simplified)
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = authService.getToken();
  if (token && req.url.startsWith('/api')) {
    req = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  }
  return next(req);
};

Registered once in app.config.ts via provideHttpClient(withInterceptors([authInterceptor])) — every outgoing request to /api/... gets the header automatically from then on.

Protecting routes

auth.guard.ts (authGuard) blocks navigation to protected routes (home, chat, patient-chat) unless AuthService.isLoggedIn() is true, redirecting to /login otherwise. A separate adminAuthGuard protects the /admin/home route the same way. Note: the guard only checks that a user object is cached locally — it does not itself re-verify the token's expiry against the server.
