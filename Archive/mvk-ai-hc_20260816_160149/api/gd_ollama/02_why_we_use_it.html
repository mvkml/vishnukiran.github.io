Why We Use It

Plain This is healthcare data. Sending patient questions to a third-party cloud AI service raises real privacy and compliance questions. Running the model locally sidesteps that entirely — nothing about a patient's conversation ever leaves this infrastructure.
  • Data never leaves the infrastructure. Every prompt and every generated answer stays local — no PHI is transmitted to an external API to get an answer.
  • Cost control. No per-token billing from a hosted model provider — running cost is just the local compute.
  • Works offline, and version-pinned. The exact model in use doesn't change underneath the application unless a deliberate ollama pull/rebuild happens — no silent behavior drift from a vendor updating a hosted model.
  • Why qwen2.5:7b specifically. It was chosen for its structured-output/function-calling strength, which matters for the query-DSL shape the assistant needs to produce (see the SQL Server section's Query-Guardrail Procedure). Medically fine-tuned models (Meditron, BioMistral) were considered and deliberately not used — this architecture grounds answers in real SQL query results, not in whatever "medical knowledge" a model happened to be trained on, so a general strong instruction- following model was the better fit.

A phased upgrade path to a larger model (Cohere's command-r, 35B parameters) is noted in the project's Ollama background documentation as a future option, not a current plan.
