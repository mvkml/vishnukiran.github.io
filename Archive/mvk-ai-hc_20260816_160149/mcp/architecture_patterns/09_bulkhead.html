Bulkhead

Resilience Pattern Real Code Example Planned MCP Host Use
Plain: A Bulkhead keeps one failing part of the system from pulling down another part that is still healthy. In this project, the principle now appears in real chat history logging code, and it is also planned for future separated MCP hosts.

What It Is

Bulkhead is a resilience pattern from distributed systems. The name comes from physical ship compartments: if one compartment floods, the whole ship should not sink. In software, the same idea means separating failure domains, capacity, or operational risk so one overloaded or broken area does not damage unrelated work.

Why, When, How

Use Bulkhead when two operations have different priorities or different failure tolerance. A user-facing response path should usually be protected from side work such as telemetry, audit enrichment, analytics, optional notifications, or calls to a lower-priority service.

The implementation can be a separate process, a separate host, a separate queue, a separate connection pool, or simply a deliberate try/catch boundary around non-critical work. The important design question is always the same: should this failure share a blast radius with that other workflow?

Real Instance In This Codebase

The concrete example is in ProviderPatientAgent.GetChatMessageContentAsync in HC.AI.MAPI.AL.Provider. The agent can produce a chat response and then persist the turn to dbo.LLMChatHistory through ILLMChatHistoryRepository.AddAsync for later analysis, guardrails, and explainability.

The Bulkhead question is whether a failed history write should make the whole chat request fail after the model has already answered. The intended design, tracked under PB065, is to isolate those paths: the chat response should still return, while the logging failure is contained and handled separately.

Why We Chose It Here

Chat response generation and chat history persistence are related, but they are not the same failure domain. A doctor or patient should not lose a valid answer only because the background record of that turn could not be saved. This gives the project a real, code-backed resilience story instead of only a future architecture diagram.

Planned MCP Host Use

ADR004 also applies Bulkhead to future MCP host segregation. Once outpatient, ICU, emergency, or other patient-data tools live in separate MCP hosts, each host can have its own capacity, deployment, timeout, and failure behavior. An overloaded Emergency tool host should not starve an outpatient query path, and an ICU host outage should not make every Doctor agent interaction fail.
