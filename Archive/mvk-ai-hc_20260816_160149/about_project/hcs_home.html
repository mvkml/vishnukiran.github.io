1. The Problem

Plain Doctors and patients need fast, natural-language access to healthcare information — "show me this patient's recent visits," "what medications is John on?" — but healthcare systems are typically locked behind rigid forms, dashboards, and technical interfaces (Swagger, SQL, admin panels) that aren't built for a conversational question. At the same time, healthcare is a field where an AI system simply making something up is not an acceptable failure mode.
Technical Two constraints drive the entire architecture: (1) the set of possible questions is effectively unbounded — hand-building a fixed REST endpoint per question doesn't scale — so the system needs to interpret open-ended natural language and translate it into a real data query dynamically; (2) letting a language model freely generate SQL or answer from its own "knowledge" is unacceptable in this domain, because a wrong-but-plausible-sounding answer about patient data is a real safety risk, not just an inconvenience.

2. The Solution

Plain A conversational AI assistant, built specifically for this domain, that always answers from real records rather than from what the model "thinks" it knows — with different personas (Doctor, Patient) getting their own tailored chat experience, secured behind proper authentication.
Technical The assistant never lets the language model generate or execute raw SQL. Instead, natural language is translated into a constrained, schema-validated query — a small structured "query DSL" — which the backend validates against an allow-list of tables/columns before executing it as parameterized, read-only data access. The model then composes its answer using only the real query result, not its own general knowledge. This closes off the two biggest risks in applying an LLM to healthcare data: SQL-injection-by-LLM, and fabricated ("hallucinated") facts about a patient.

3. How It Works

Plain A question goes through a chain of checks and translations before it ever touches patient data, and the answer that comes back is built only from what was actually found — the AI is a translator and communicator, not the source of truth.
Doctor/Patient asks a question in the chat UI → Authenticated request reaches the AI Assistant API → Orchestration layer (Semantic Kernel) selects the right model for this persona/request → Local LLM (Ollama) interprets intent, proposes a structured query — not raw SQL → Guardrail layer validates the query against an allow-list (read-only, known tables/columns only) → Query executes against SQL Server, real results come back → LLM composes the final answer using only those results → Answer is returned to the chat UI
Technical Implemented as a layered ASP.NET Core backend (HC.AI.MAPI): Controller → Service Layer → Semantic Kernel orchestration → LLM connector (Ollama) → Prompt Layer → Guardrail Layer → Tool Layer → Business/Repository/EF Core → SQL Server. Every stage owns one responsibility, so guardrail logic, prompt content, and model selection can each evolve independently without touching the others. Model and prompt selection is being migrated from static configuration to a database-backed, per-persona configuration (in progress) so behavior can be tuned without a redeploy.

7. Client Demo Framing

Plain The demo story is simple: this is Healthcare Co-Pilot Studio starting with real user journeys, not a generic chat application. A doctor or patient signs in, asks a healthcare question, and the platform routes that question through identity, persona rules, model orchestration, guardrails, and real data before returning an answer.
Technical The client value is the combination of architecture and delivery discipline: Angular for the persona UI, ASP.NET Core for the API boundary, Semantic Kernel for orchestration, Ollama for local model execution, SQL Server for governed healthcare data/configuration, Playwright for regression confidence, and Azure DevOps for traceable backlog management. Each layer is documented separately so the project can be discussed with product, architecture, engineering, QA, or delivery stakeholders.
